# Winsome — Design

Decisions with rationale. If code disagrees with this doc, one of them is wrong — fix whichever it is, in the same PR.

## Goals

1. **Omakase**: one command in, a finished desktop out. Curation over configuration.
2. **Muscle-memory portability**: omarchy's keybinding grammar, verbatim, on a mod key that exists in the same physical spot on a future omarchy machine (`caps:super`). Hands trained here work there.
3. **Omarchy theme compatibility**: real omarchy theme folders in, themed Windows desktop out. Stock and community themes.
4. **Stock Windows where Windows wins**: PowerToys, Win+V, built-in OCR/dictation stay. Winsome never rebuilds what the OS already ships.
5. **Reversible and honest**: manifest-driven uninstall, disable-without-uninstall, loud failure. Documented gaps stay documented, not papered over.
6. **Scriptable throughout**: every action a CLI verb, every config a file. Agents (human or AI) can drive the whole thing.

## Architecture

```
kanata (elevated, LLHOOK)         — caps → right-Win (pure modifier, nothing else)
  └─> GlazeWM (user-level)        — tiling, omarchy grammar bound as rwin+X in YAML
        └─> Zebar                 — per-monitor top bar (taskbar hidden)
winsome-helper                    — wallpaper/monitor, light-dark, taskbar, audio
winsome supervisor                — start order, restart-on-crash, monitor-replug bounce, health
theme adapter                     — omarchy theme folder -> rendered Windows configs
winsome CLI                       — theme|bg|update|render|toggle|keys|doctor
```

### Key decisions and why

**GlazeWM as base tiler, not komorebi.** komorebi is technically richer (deeper CLI/IPC), but its license (Komorebi 2.0.0, a PolyForm Strict fork) prohibits redistribution and requires a paid license for workplace use — undistributable as the core of an open-source project. GlazeWM: GPL-3.0, 12k+ stars, V3 Rust rewrite, YAML config, `focus_follows_cursor`, border effects, per-monitor workspaces. komorebi returns later as a bring-your-own-license power option (`winsome-wm-switch`, the omacosy AeroSpace/OmniWM pattern). **Known risk (2026-08-28): GlazeWM upstream is dormant** — no commit to main since 2026-04-08, 40+ open PRs, maintainer publicly inactive; mitigated by pinned versions, the supervisor owning failure modes, and GPL fork as worst case. Field re-swept at that date; GlazeWM still wins as default (see `docs/research/gap-features.md`).

**kanata runs elevated with the LLHOOK backend; the Interception driver is never installed.** Two problems, one move: (a) UIPI starves a user-level keyboard hook when an admin window has focus — an elevated hook process sees those keys; (b) the Interception kernel driver is on anti-cheat blocklists (FACEIT names it) — LLHOOK is the same user-mode API PowerToys uses, uncontroversial. Elevated kanata reads its config from an ACL-protected path (an elevated process must not execute user-writable config). Residual: kernel anti-cheat games can ignore synthetic input in-game — a game-foreground auto-suspend toggle covers it.

**Mod key: caps → right-Win, settled by spike evidence and source review.** kanata maps Caps Lock to `rmet` (right Win) as a pure modifier — nothing else — and GlazeWM binds `rwin+X` chords (its keyboard hook matches `rwin` bindings against VK_RWIN only, verified in GlazeWM source), so the **physical left Win key keeps 100% native Windows behavior**. Every cleverer design failed live: synthesized multi-modifier chords and output-chord layers desync kanata (its `GetAsyncKeyState` reconciliation force-clears state when GlazeWM's hook consumes a key kanata tracks — being tracked by kanata and consumed by GlazeWM are structurally mutually exclusive, confirmed in kanata source `src/kanata/windows/llhook.rs`); tap-hold with unprocessed keys races; per-press process spawns cost 60-100ms. The hyper-chord idea additionally collides with the Office key (Ctrl+Alt+Shift+Win). Shift-variants need nothing: GlazeWM reads physical Shift natively. Losses accepted: Caps+L is unbindable (Win+L is winlogon-level; omarchy's Super+L maps to a layout GlazeWM lacks anyway), and **tap-caps-as-launcher is deferred** — structurally impossible on native bindings today; the fast-follow is a resident relay (winsome.exe holds a warm WebSocket to GlazeWM's IPC plus a TCP link to kanata, with a small upstreamable kanata "notify" action replacing process spawns — single-digit ms). Until then the launcher is Caps+Space (omarchy's actual Super+Space). `apps` mode (VK_APPS as the mod) remains the config alternative. ScrLk → raw CapsLock ships in every config as the escape hatch.

**The keymap is omarchy's, verbatim, as a tiler-agnostic mapping file.** `keymap/omarchy.toml` carries every binding upstream (quattro) ships — 226 chords — each either mapped to GlazeWM commands or carrying an explicit gap/native/app/omitted status with its reason; `winsome keymap render` generates the GlazeWM `keybindings:` section, `check` validates and prints coverage. The mapping file tracks upstream omarchy; grammar drift shows up as a diff, not a surprise. Three deliberate deviations, each also marked `deviation` in the file: (1) SUPER+TAB keeps omarchy's next-workspace meaning (the spike's temporary cycle-focus use is reverted); (2) the fullscreen focus-trap escape (`wm-cycle-focus`, spike finding) lives on SUPER+ESCAPE, whose omarchy meaning (system menu) has no Windows analog; (3) Alt+Tab stays native Windows rather than shadowed. Accepted losses recorded in the file: SUPER+L (winlogon-level), mouse bindings (GlazeWM lacks them), universal clipboard chords (would reintroduce the two-hooks desync). Personalization stays out of the repo: `keymap/local.toml` under the Winsome home merges over the stock file at check/render — `[apps]` command overrides (one line retargets every chord using that placeholder), `[[bind]]` entries added or replaced by id, `disable`d stock ids — and the merged result is revalidated, so a dangling reference or a local bind grabbing a taken chord fails loudly. Machine-local facts (Chrome profile directories, editor paths) belong there, never in `omarchy.toml`.

**Render, don't symlink.** Windows symlinks want admin/dev-mode and tools clobber them. The repo holds source-of-truth defaults plus git-ignored `*.local` overrides (omacosy's `apps.conf` pattern); `winsome render` writes each tool's real config to its expected path, backing up anything pre-existing.

**Supervisor is a hard requirement, not defense.** A dead tiler on Windows leaves a normal-looking desktop with hotkeys silently gone — worse than a crash. The supervisor owns: start order (kanata → GlazeWM → Zebar), restart-on-exit, display-change awareness, and a health indicator in the bar. Display changes are always **logged**; the automatic pair bounce (`bounce_on_display_change`) ships **off** — glzr-io/glazewm#1233 reports reconnected monitors needing a restart, but the M0 spike could not reproduce it on 3.10.1 (a full occasional-display add/remove/re-add cycle ran clean, workspaces intact), and monitor-set change is a *routine workflow* here (a display toggled on only for teleprompter use), so bouncing on every toggle would manufacture the very disruption the bounce exists to fix. The log ties any future #1233 sighting to its replug; the flag is the one-line response. Workspaces bind to the daily displays; an occasional display gets no workspace auto-assignment, so toggling it never reshuffles the primaries.

**Supervisor hosting: user-level at logon; kanata reached through its task; adopt before start.** The supervisor cannot be elevated — everything GlazeWM spawns inherits its token, so GlazeWM and therefore its parent must stay user-level — yet kanata must be elevated (UIPI). The resolution is that the supervisor drives kanata *through* the pre-registered elevated `WinsomeKanata` task: start = `schtasks /run`, stop = `schtasks /end`, both UAC-free for the task's owner (the Task Scheduler service does the killing), liveness watched via a pid handle found by exact image path. Verified live 2026-08-28: `/end` from a non-elevated shell terminated elevated kanata; the supervisor restarted it via `/run` in ~1.3s. Two more hosting facts, both learned live the same night: (1) components whose exact executable is already running are **adopted** (watched, not restarted) — the supervisor slides under a live desktop without bouncing it, and a returning supervisor never double-spawns; (2) GlazeWM's manifest is `asInvoker` + `uiAccess="true"`, which makes plain `CreateProcess` fail with `ERROR_ELEVATION_REQUIRED` (740) — the supervisor falls back to `ShellExecuteExW` (the AppInfo path that may grant UIAccess) and keeps the returned process handle. Task-hosted, adopted, and shell-launched components have no captured stdio; only direct children do. The logon task runs `winsomed.exe`, a GUI-subsystem twin of `winsome supervise` (a console binary in a logon task puts a console window on the desktop); session end reaches it as `WM_ENDSESSION` on the display watch's window, feeding the same graceful-shutdown flag as Ctrl+C. `winsome down` returns only when the shutdown has *finished*, not when it was heard — the panic path proved the difference matters (a caller that killed the supervisor after the ack orphaned the pair mid-shutdown). Panic itself therefore goes through `winsome down` first and force-sweeps only after: killing components while the supervisor lives means the desktop refuses to die.

**Theme adapter: colors.toml is the sole palette source.** Omarchy 4 (Quattro) themes ship a flat `colors.toml` with 26 semantic keys, verified against the raw v4.0.1 files across multiple themes: `mode` (`"dark"|"light"`), `accent`, `selection`, `muted`; `background` + `dark_`/`darker_`/`lighter_background`; `foreground` + `dark_`/`light_`/`bright_foreground`; eight named colors (`red`, `yellow`, `orange`, `green`, `cyan`, `blue`, `magenta`, `brown`); six `bright_*` variants. **Terminal ANSI mapping mirrors omarchy's own `default/themed/ghostty.conf.tpl`** (slot 0 = background, 7 = foreground, 8 = muted, 15 = bright_foreground, cursor = bright_foreground) — adopted verbatim, never invented. `mode` is authoritative for light/dark; the luminance fallback exists only for legacy themes. A theme without a parseable 26-key colors.toml fails loud ("couldn't parse this theme"), never silently mis-themes; waybar.css is never parsed. Earlier formats (v3-era color0-15 files, pre-v3 alacritty.toml themes) are a deferred legacy fallback, not v1. Render targets: Windows Terminal scheme, Zebar stylesheet (our template), GlazeWM border colors, per-monitor wallpaper (IDesktopWallpaper), Windows light/dark (from `light.mode` marker, falling back to background luminance), Neovim (pass-through of the theme's own `neovim.lua` colorscheme — no generation), VS Code (pass-through of the theme's shipped `vscode.json`), Chromium frame tint (`BrowserThemeColor` policy — pending verification). Per-app compact-chrome settings for curated apps ride along with render.

**Language: Rust, one static binary.** `winsome.exe` is the CLI, the supervisor, and the theme adapter in one artifact — no Node, no PowerShell-version dependency for users. Chosen because the entire component stack (kanata, GlazeWM, Zebar) is Rust, and a supervisor wants native process control. The bootstrap-era TypeScript adapter was the reference implementation; it is ported to `crates/winsome-theme` with its golden tests and then retired. PowerShell remains only for install-time scripts.

**Panic is a product feature.** A busted keyboard stack must always leave a one-gesture exit (spike incident: kanata died, chords vanished, raw Win presses fired OS shortcuts). Layers: the supervisor's linked-pair rule handles it automatically; beneath that, a pre-registered elevated `WinsomePanic` scheduled task (UAC-free to trigger) kills the stack and restores the taskbar — bound to mod+Shift+Q, findable in the launcher as "Winsome Panic", plus kanata's built-in Ctrl+Space+Esc and the ScrLk raw-CapsLock hatch.

**Logging is foundational, not a retrofit.** The M0 spike's hardest bug (kanata/GlazeWM hook desync) was only diagnosable because a console happened to be open. Therefore: the supervisor captures every component's stdout/stderr to `~/.winsome/logs/<component>.log`, rolling (size-capped, N-day retention); components run headless (no consoles, no log windows). `winsome logs <component>` tails; `winsome doctor` summarizes recent errors per component; `winsome debug on|off` flips each tool's verbose flag (kanata `--log-level debug`, etc.) and is the first move of any diagnosis. A failure that leaves no log line is a supervisor bug.

**Install**: `irm …/install.ps1 | iex` → scoop (no admin) → pinned versions from the winsome scoop bucket → clone to `~/.winsome` → render → one elevation prompt registers the elevated tasks (`WinsomeKanata` on-demand, `WinsomePanic`); `WinsomeSupervisor` (at logon, user-level, running `winsomed.exe`) needs no elevation. Binaries are copied to `~/.winsome/bin` so a running supervisor never locks the build tree (`installer/register-tasks.ps1` is the dogfood-era version: idempotent, re-run after a rebuild). No driver, no reboot. `winsome update` = git pull (refuses on dirty tree) + re-render + restart. Bootstrap disables PowerToys Keyboard Manager's caps remap and FancyZones (both double up on kanata/GlazeWM territory; hook order is unstable across reboots) — KBM's ScrLk→Caps remap stays as the kanata-dead backup hatch.

## Documented gaps (permanent or deferred)

- **Titlebars: solved.** GlazeWM's `hide_title_bar` effect (Windows 11) verified in the M0 spike: classic-chrome windows get their titlebar shaved; modern apps draw their own chrome and are unaffected. Default-on with per-app opt-out.
- **Chrome frame tint works but is blunt**: `BrowserThemeColor` policy requires HKLM on hardened machines (HKCU `Software\Policies` can be ACL-locked — observed), applies on Chrome's lazy policy refresh (minutes after the registry write, not at launch), and overrides user-installed themes across **all** profiles — spike-verified. That uniformity destroys per-profile color-coding, so Winsome ships it opt-in; per-profile generated theme extensions are the surgical answer (deferred).
- **Notifications unthemed** — Windows toasts render in ShellExperienceHost; no lever exists.
- **Elevated windows float untiled** — GlazeWM runs user-level; UIPI blocks managing admin windows. Keys still work in them (kanata is elevated).
- **Window grouping/tabs (omarchy mod+G) absent** — GlazeWM has no grouping primitive (full IPC verb enum verified 2026-08-28) and upstream is dormant with its own stacking attempts abandoned; unfixable from outside the WM. mod+G binds to a notification stub pointing at the komorebi power option (the only genuine grouping on Windows). Decision record: `docs/research/gap-features.md`.

## Verification strategy

Layered; everything below "manual" runs in CI or a single script.

**Unit (CI, windows-latest):**
- Theme adapter is pure functions → golden-file tests: all 19 stock omarchy themes render to snapshotted outputs (WT scheme JSON, Zebar CSS, GlazeWM YAML fragment). Luminance-fallback cases, malformed/missing colors.toml fail-loud cases.
- Rendered GlazeWM config: YAML parses, required keys assert.
- kanata configs: `kanata --check` in CI; tap-hold behavior via kanata's simulated-input mode (grammar tests without hardware).
- Installer PowerShell: Pester — manifest correctness, idempotency (two runs, identical state), path/ACL assertions.

**Integration (scripted, local or sandbox):**
- Supervisor: kill each child, assert restart + health state; fake display-change event, assert GlazeWM bounce.
- Install e2e in Windows Sandbox: clean install → assert stack up → uninstall → assert pre-install state restored (manifest diff).

**Desktop UAT (scripted state assertions, not vision):**
- Harness spawns real windows (terminal instances), injects real keystrokes via SendInput, asserts outcomes through GlazeWM's IPC state queries: mod+2 → focused workspace is 2; mod+Shift+arrow → window swapped; launcher tap → process appeared. Real keys through the real kanata → real tiler — end-to-end without a human.
- Theme visual pass: script switches through all themes capturing per-theme screenshots; reviewed by eye (agent or human) and doubling as README/gallery assets.

**Manual (release gate):** one human hour on the real triple-monitor rig — sleep/wake, monitor replug, admin terminal, game launch, PowerToys coexistence.
